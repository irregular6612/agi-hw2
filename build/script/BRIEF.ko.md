# 발표 대본 BRIEF (ko, 주현 말투)

## 무엇을 쓰나
덱의 build(클릭 한 번 = 슬라이드 한 장)마다 발표자가 실제로 소리 내어 말할 한국어 대본. 슬라이드 노트에 들어간다.
한국어 리허설용 초안이고 나중에 영어로 옮긴다. 발표자는 주현(Juhyeon Park). 청중은 AGI 대학원 수업 수강생(Transformer는 알지만 looped 연구는 처음).

## 입력
- `build/out/manifest.json` — build별 `key`, `title`, `onSlide`(화면 글자), `notes`(기존 영어 메모, 사실 근거로 사용), `cite`.
- `storyline.md` — 전체 서사(Q1–Q4 질문 원장). 자기 절 앞뒤 흐름을 먼저 본다.
- `sources/<paper>.md` — 논문별 검증 다이제스트. 슬라이드에 없는 사실은 여기 있는 것만, 최소로.
- 말투: `~/.claude/skills/ditto-writer/profiles/juhyeon-ko-academic/profile.md` (Never·습관·persona·강점 규칙·anchor). anchor는 문체용이고 내용은 쓰지 않는다.

## 말투: 프로필을 발표 구어로 옮기는 규칙
- 종결은 합니다체(-습니다/-ㅂ니다). -요체와 반말은 쓰지 않는다. 주장은 평서 단정, 헤지는 `수 있습니다`로 경쟁 설명에만.
- 1인칭은 `저희는`(팀 해석). 청중 호명 `여러분`은 절마다 1회 이하.
- 단문을 build의 첫 문장이나 끝 문장에 둔다. 문장은 말하기 좋게 짧게(평균 8–14어절). 쉼표는 적게, 문두 `따라서`·`그래서` 뒤 쉼표 없음.
- 강점 규칙을 덱 구조에 맞춘다.
  - 질문 재설정 네 박자 = 질문 원장. 표지(cover)에서 원 질문을 말하고, 절 안에서 그 질문을 어떤 비교로 확인할지로 바꾸고, `Answer to Qn`에서 원 질문에 직접 답한다.
  - 기준은 입장보다 먼저. 비교 슬라이드(iso-param/iso-FLOP, MoR 토큰 수, Ouro 대조군)에서는 무엇과 무엇을 비교해야 공정한지 먼저 말하고 결론을 말한다.
  - 추상어는 화면의 수치·그림 속 위치로 내린다. 절 끝 build는 다음 절이 답할 질문으로 연다(수사 의문은 절마다 2회 이하).
- Never (프로필 §1 + 발표판)
  - 대시(—, –), 콜론, 세미콜론, 느낌표, 말줄임, 직선 따옴표. 따옴표가 필요하면 ‘ ’ “ ”.
  - `다양한`, `핵심적`, `중요한 역할`, `이는 ~를 보여줍니다`, `~할 수 있을 것입니다`, `단순히 A가 아니라 B`, `~라는 점에서`.
  - 자문자답 뒤 짧은 단답 (`왜일까요? 바로 ~입니다.`), 슬로건 한 줄 마무리, 예고 후 나열 (`세 가지를 보겠습니다. 첫째`), 매 build 같은 문장 틀.
  - 화면 영어 문장을 한국어로 그대로 옮겨 읽기. 대본은 화면을 보충한다. 왜 이 장면을 보는지, 그림의 어디를 봐야 하는지, 그래서 무엇을 알게 됐는지.
  - `금색 박스를 보시면` 같은 지시 문구 반복. 위치는 그림 내용으로 가리킨다(`왼쪽 파란 막대`, `가운데 블록`). 지시 문구는 절마다 2회 이하.
  - (r1 블라인드 두 리뷰어 공통) 서로 다른 근거를 네 절·두 절 평행으로 맞춘 종합문, 교차 대구(`A지만 B이고, C지만 D입니다`), 개념 정의로 끝맺는 격언풍 결론, 앞 문장을 되받아 대칭을 만드는 문장.
  - 같은 자리 반복: 증거 끝의 `다만` 단서(덱 전체 6회 이하, 단서는 수치 앞에 미리 말해도 된다), `X이지 Y가 아닙니다`(덱 전체 3회 이하), 묻지 않은 오해를 먼저 부정하기, 질문 행선지 안내(`Q3가 받습니다`, 넘기는 질문은 하나만 말한다), `저희는 ~라고 읽습니다`.
  - Answer 장마다 같은 틀(질문 복창 → 예 → 수치 재나열 → 다만 → 다음 Q). 장마다 순서를 바꾸고 수치는 하나만 다시 말한다.

## 사실 규칙
- 수치·이름·연도는 화면(onSlide), 기존 notes, sources 다이제스트에 있는 것만. 화면 수치와 같은 자릿수로 말한다.
- 고유명·모델명·지표명은 화면 영어 표기 그대로 (Huginn, MMLU, FLOP, iso-param). 일반 명사는 한글 표기로 통일 (루프, 파라미터, 토큰, 층, 루프 모델). chain of thought는 처음 한 번 `chain of thought, 줄여서 CoT`, 이후 CoT.
- `[ours]` 상자는 말로도 표시한다. 논문의 주장이 아니라 저희 해석이라는 것을 한 문장으로 밝힌다.
- 증거가 약한 곳(seed 1개, 보도 1건, 증명만 있음)은 화면에 적힌 만큼만 말하고 부풀리지 않는다.

## 길이 (시간 예산)
- 단위: 한글 음절 + 영어 단어당 1.5 + 숫자 묶음당 2. 280단위 = 1분. build마다 클릭 1.5초가 더해진다.
- 자기 절 합계가 목표 시간의 −10% ~ +3% 안. 확인: `node build/count.js <section>` (절 파일만 읽는다; build.js는 돌리지 않는다).
- build별 가이드: 그림 단계 build 40–90단위(10–20초), Remark 40–80, 표·막대 공개 build 50–110, 아이디어 슬라이드 100–220, 표지 80–150, Answer 150–250, 토론 질문 60–120(시간 예산 밖).
- 그림 단계 build는 앞 단계에서 이어 말한다. 같은 그림의 첫 build에서만 그림 전체를 소개한다.

## 형식
- 파일: `build/script/ko/<section>.md`. 첫 줄 `# <section>`. manifest 순서대로 모든 key에 `## <key>` 헤딩 하나.
- 본문은 말할 문장만. 목록·굵게·주석·무대 지시 없음. 문단은 build당 1–2개.
- Session A 첫 장(title)은 인사와 오늘의 질문 한 문장으로 연다. Session A 마지막(handoff)은 Session B로 넘기는 말로 끝낸다. 발표자 이름은 쓰지 않는다(A/B 배정 미정).

## 자체 점검 (제출 전)
1. `node build/count.js <section>`: MISSING 0, unknown 0, 목표 범위 안.
2. `grep -nE '—|–|:|;|!|…|"|다양한|핵심적|중요한 역할|보여줍니다|것입니다|라는 점에서' build/script/ko/<section>.md` → 대본 본문에서 0건 (헤딩의 key는 제외).
3. 대본의 모든 숫자가 해당 build의 onSlide·notes 또는 sources 다이제스트에 있다.
4. 연속한 build 3개가 같은 문장 틀로 시작하지 않는다.
